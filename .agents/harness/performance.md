# Performance Harness

성능 분석·개선과 성능 수치가 포함된 보고는 반드시 이 규칙을 따른다. 일반 구현·보안·승인·검증 규칙은 루트와 대상 폴더의 `AGENTS.md`가 우선한다.

## 필수 흐름

1. 대상 API·사용자 흐름, 기대 부하, 성공 기준과 변경 범위를 정의한다.
2. 코드에서 병목 후보를 찾되 아직 측정하지 않은 판단은 `가설`로 표시한다.
3. 코드를 변경하기 전에 Baseline을 측정하고 원본 결과와 테스트 시각을 보존한다.
4. 부하와 같은 시간대의 SQL·애플리케이션·인프라 지표로 병목 가설을 확인하거나 기각한다.
5. 최소 두 가지 개선 후보의 기대 효과, 부작용, 복잡도와 운영 위험을 비교한다.
6. 근거에 가장 가까운 최소 변경을 구현하고 기능 회귀 테스트를 실행한다.
7. Baseline과 동일한 조건으로 After를 측정한다.
8. 최종 결과를 `문제 → 의사결정 과정 → 결과(실측 수치)` 순서로 보고한다.

## Evidence Rule

다음 판단은 하나 이상의 직접 근거와 출처를 함께 제시할 때만 사실로 표현한다.

- `병목`, `N+1`, `DB가 느림`, `인덱스 필요`, `캐시 필요`, `커넥션 풀 고갈`
- `응답 시간이 개선됨`, `처리량이 증가함`, `부하가 감소함`, `성능 기준을 충족함`

허용 근거는 k6 원본 결과, 요청별 SQL 수와 SQL 로그, `EXPLAIN`·실행계획, 프로파일링 결과, Prometheus 쿼리·Grafana 패널, JVM·GC·스레드·DB pool 지표, 코드상 명확한 호출 구조다. 코드 구조만으로 실제 발생 여부나 영향도를 단정하지 않는다. 근거가 없거나 상충하면 `가설`, `미확인` 또는 `기각`으로 기록한다.

## 비교 가능 조건

Before와 After에서 아래 조건을 고정하고 보고서에 기록한다.

- 애플리케이션 버전과 설정, 실행 환경과 인프라 자원
- API·사용자 흐름, 인증과 요청 비율
- 데이터셋의 크기·분포·식별자와 cache warm/cold 상태
- k6 스크립트, executor, VU 또는 arrival rate, stage, duration, think time
- 네트워크 경로, 사전 warm-up, 모니터링 구간

조건이 다르거나 확인되지 않으면 직접 비교하거나 개선율을 계산하지 않는다. 차이를 명시하고 재측정한다.

## 필수 결과

가능한 범위에서 Average, p95, p99, RPS, Error Rate와 요청당 SQL 수·쿼리 시간, CPU, Memory, JVM Heap·GC, Thread, HikariCP active/pending/max를 Before/After로 제시한다. 측정하지 못한 항목은 `N/A`와 사유를 쓰며 숫자를 추정하지 않는다. 감소형 지표 개선율은 `(Before - After) / Before × 100`, 증가형 지표는 `(After - Before) / Before × 100`으로 계산하고 단위와 원본 근거를 남긴다.

## 안전 경계

- 운영 환경에 임의로 부하를 주지 않는다. 승인된 격리 환경이 없으면 스크립트와 실행 계획까지만 작성한다.
- Secret·실제 토큰·개인정보를 테스트 코드나 결과에 저장하지 않는다.
- 인덱스·스키마 migration, 운영 설정, 배포는 사전 승인 없이 실행하지 않는다.
- 하나의 실행만으로 결론내리지 않는다. 변동성을 확인할 수 있게 같은 조건을 반복하고 실행별 결과를 숨기지 않는다.
