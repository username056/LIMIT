## 0. 문서 기준과 확인 범위

- 작성 기준 소스: `origin/dev`
- 기준 커밋: `21a0251e2ea27a8a1e47294b3c379a665f188df7` (`21a0251`, 2026-08-10)
- 저장소: `https://lab.ssafy.com/s15-webmobile1-sub1/S15P11C203.git`
- 작성일: 2026-08-10
- 범위: 소스 클론, 로컬 빌드·실행, 운영 배포, 환경변수, DB 연결 및 설정 파일

이 문서는 실제 Secret 값을 포함하지 않는다. 실제 `.env`, 토큰, 비밀번호, 개인키, 인증서는 GitLab protected/masked 변수 또는 운영 서버 전용 파일로 전달한다.

> 브랜치 주의사항: 현재 원격 기본 브랜치는 `origin/dev`이며 원격 `main` 브랜치는 존재하지 않는다. `origin/master`는 현재 개발 소스와 다른 초기 상태의 브랜치다. 저장소 규칙과 CI는 `dev`와 `main`을 배포 브랜치로 가정하므로, 최종 운영 이관 전에 `main` 생성·보호 정책을 팀에서 확정해야 한다. 이 문서는 임의로 `master`를 `main`으로 간주하지 않는다.

## 3. 로컬 실행

### 3.1 권장 실행: Docker Compose

필수 도구는 Git, Docker Desktop, PowerShell이다. 다음 스크립트는 `infra/.env.local`이 없으면 로컬 전용 DB 비밀번호와 JWT Secret을 난수로 생성하고, Backend·MySQL·MongoDB·Redis·모니터링 컨테이너를 빌드·기동한 뒤 Swagger와 Grafana readiness를 확인한다.

```powershell
.\scripts\open-platform-tools.ps1
```

브라우저를 자동으로 열지 않으려면 다음과 같이 실행한다.

```powershell
.\scripts\open-platform-tools.ps1 -NoOpen
```

동일한 Compose 명령은 다음과 같다.

```powershell
docker compose --env-file infra/.env.local `
  -p limit-local `
  -f infra/compose.yml `
  -f infra/compose.local.yml `
  up -d --build
```

프론트엔드는 별도로 실행한다.

```powershell
cd frontend
npm ci
npm run dev
```

| 서비스 | 로컬 주소·포트 |
| --- | --- |
| Frontend | `http://localhost:5173` |
| Backend / Swagger | `http://localhost:18080`, `http://localhost:18080/swagger-ui.html` |
| MySQL | `localhost:13306` |
| MongoDB | `localhost:17017` |
| Redis | `localhost:16379` |
| Grafana | `http://localhost:3000` |

종료:

```powershell
docker compose -p limit-local down
```

| --- | --- | --- |
| MySQL | `MYSQL_USER` / `MYSQL_PASSWORD` | Backend 애플리케이션 계정 |
| MySQL | `MYSQL_ROOT_PASSWORD` | 초기화·관리·백업용 root 계정 |
| MongoDB | `MONGODB_ROOT_USER` / `MONGODB_ROOT_PASSWORD` | 초기 root 계정 |
| MongoDB | `MONGODB_URI` | Backend 연결 URI; `authSource=admin` 포함 여부 확인 |
| Redis | `REDIS_PASSWORD` | Backend와 exporter 인증 |
| Grafana | `GRAFANA_ADMIN_USER` / `GRAFANA_ADMIN_PASSWORD` | 대시보드 관리자 |
| 애플리케이션 | `INITIAL_ADMIN_*`, `BASE_INIT_ADMIN_*`, `BASE_INIT_MEMBER_*` | 최초·시험 계정 생성에만 사용 |

실제 계정명·비밀번호는 이 문서나 Git에 기록하지 않는다. 최초 관리자와 base-init 플래그는 필요한 최초 1회에만 `true`로 바꾸고 생성 직후 `false`로 되돌린다.

### 5.2 설정·스키마 파일 목록

| 경로 | 내용 |
| --- | --- |
| `backend/src/main/resources/application.yml` | 공통 Spring 설정, 인증, 메일, 결제, S3, AI, OCR 등 |
| `backend/src/main/resources/application-local.yml` | 로컬 MySQL·MongoDB·Redis 연결과 Swagger 설정 |
| `backend/src/main/resources/application-prod.yml` | 운영 DB·JWT·readiness 설정 |
| `infra/compose.yml` | MySQL·MongoDB·Redis 이미지, volume, internal network |
| `infra/compose.local.yml` | 로컬 포트와 환경변수 override |
| `infra/compose.prod.yml` | 운영 Blue/Green Backend, DB, TURN, 모니터링 |
| `infra/.env.example` | Compose와 Backend 환경변수 예시 |
| `backend/src/main/resources/db/migration/` | Flyway migration의 권위 있는 원본 |
| `docs/db/전체_ddl.sql` | 전체 DDL 참고본. migration보다 우선하지 않음 |
| `docs/integration/database-schema-runbook.md` | 스키마 운영 절차 |
| `infra/secrets/*.example` | exporter·Alertmanager Secret 파일 예시 |

운영 DB 포트는 외부에 공개하지 않고 Compose internal network에서만 접근한다. 로컬에서만 MySQL 13306, MongoDB 17017, Redis 16379 포트를 호스트에 노출한다. JPA 운영 설정은 자동 스키마 변경 대신 `ddl-auto=validate`를 사용하고, 실제 스키마 변경은 Flyway migration으로 수행한다.

## 6. 운영 배포

### 6.1 구조

- Frontend: private S3 정적 파일 + CloudFront OAC, `l1mit.shop` / `www.l1mit.shop`
- Backend: 단일 EC2의 Docker Compose, Blue/Green Backend 컨테이너
- Web server: 호스트 Nginx 443 reverse proxy
- Data: MySQL·MongoDB·Redis는 Docker internal network
- RTC: coturn
- Monitoring: Prometheus·Loki·Grafana·Alertmanager·exporter
- 운영 배포 루트: `/opt/limit`
- 기존 Apache/Gerrit 8989 설정은 건드리지 않는다.

### 6.2 GitLab Pipeline

주요 흐름은 `guard → test → quality → package → deploy → verify`다.

1. Gitleaks와 계약 검사를 수행한다.
2. Backend unit/integration test, Frontend lint/test/build, Scanner test/publish를 수행한다.
3. Backend JAR와 Docker 이미지를 만들고 Trivy로 검사한다.
4. Docker Hub에 push한 immutable digest를 배포 artifact로 전달한다.
5. 배포 스크립트와 Compose·Nginx·모니터링 파일을 EC2에 동기화한다.
6. 서버 전용 `infra/.env`, `infra/secrets`, `infra/state`는 덮어쓰거나 삭제하지 않는다.
7. 비활성 색상 Backend를 기동하고 `/actuator/health/readiness`를 확인한다.
8. Nginx upstream을 전환한 뒤 외부 `/health` smoke test를 수행한다.
9. 성공하면 이전 색상을 중지한다. 실패하면 기존 upstream을 복원한다.
10. Frontend는 `frontend/dist`를 release 경로에 업로드하고 마지막에 `index.html`을 교체한 뒤 CloudFront invalidation과 smoke test를 수행한다.

운영 상태 확인 예시:

```bash
cd /opt/limit
docker compose --env-file infra/.env -p limit-prod \
  -f infra/compose.yml -f infra/compose.prod.yml ps
curl -fsS https://api.l1mit.shop/health
```

수동 rollback은 GitLab의 보호된 `rollback_prod` job을 사용한다. Backend는 반대 색상 컨테이너에 남은 이전 immutable digest를 선택하고, Frontend는 `FRONTEND_ROLLBACK_RELEASE`에 이전 commit SHA를 지정한다.

### 6.3 배포 전 확인사항

- 운영 `infra/.env`와 `infra/secrets/*` 권한 및 누락 여부
- `BACKEND_BLUE_IMAGE`, `BACKEND_GREEN_IMAGE`가 tag가 아닌 검증된 digest인지 여부
- Flyway migration의 하위 호환성과 expand-and-contract 적용 여부
- DB backup 생성·복구 가능 여부
- OAuth callback URL, Toss webhook, S3 CORS·IAM, TURN credential
- Nginx 설정 문법과 기존 Gerrit 8989 미변경 여부
- readiness, 외부 `/health`, 주요 사용자 흐름 smoke test
- 로그에 토큰·개인정보가 출력되지 않는지 여부
- 현재 원격에 없는 `main` 브랜치와 GitLab protected branch/CI rule 정합성

기존 운영 문서에는 GitLab OIDC provider와 Frontend 배포 role이 아직 생성되지 않았다는 기록이 있다. 이 상태는 시점 의존적이므로 실제 GitLab·AWS 콘솔에서 재확인하고, 미구성이라면 Frontend 자동 배포는 AWS 인증 단계에서 실패한다.

## 7. 확인된 미정 사항

- Windows Scanner에 사용한 Visual Studio 제품·정확한 버전은 확인되지 않았다. C#, .NET 8, SDK 8.0.415, WinForms만 확정했다.
- IntelliJ IDEA와 VS Code는 일부 팀원이 사용한 개발 도구이며 팀 전체의 필수 IDE로 단정하지 않는다.
- 외부 서비스의 실제 계정명, 프로젝트 ID, bucket명, distribution ID, token 값은 인수인계 범위에서 제외했다. 가입·설정 절차와 필요한 변수명은 `exec/외부_서비스_정보.md`에 정리했다.
