# L1MIT 외부 서비스 가입·설정 정보

## 0. 문서 범위

- 작성 기준: `origin/dev` 커밋 `21a0251`
- 실제 계정명, 프로젝트 ID, 애플리케이션 ID, bucket명, 결제 상점 ID, 토큰 값은 기재하지 않는다.
- 가입 위치, 서비스 용도, callback·webhook 등 계약, 필요한 환경변수 이름까지만 정리한다.
- 모든 Secret은 담당 조직 계정으로 발급하고 GitLab masked/protected 변수 또는 운영 서버 Secret에 저장한다.

서비스 콘솔의 메뉴명과 화면은 변경될 수 있다. 아래 공식 문서와 저장소의 현재 설정 계약을 함께 확인한다.

## 2. 소셜 로그인

세 공급자 모두 Backend가 Authorization Code를 토큰으로 교환한다. Client Secret은 Frontend에 넣지 않는다. Backend의 OAuth 기능은 공급자별 `*_OAUTH_ENABLED=false`가 기본값이다.

공통 임시 상태 변수:

- `OAUTH_ATTEMPT_STORE=redis`
- `OAUTH_STATE_TTL=10m`
- `SOCIAL_SIGNUP_STORE=redis`
- `SOCIAL_SIGNUP_TTL=15m`
- Frontend: `VITE_OAUTH_REDIRECT_BASE_URL`

### 2.1 Google OAuth 2.0

공식 문서: [Google OAuth 2.0](https://developers.google.com/identity/protocols/oauth2)

가입·설정:

1. 조직이 관리하는 Google 계정으로 Google Cloud Console에 로그인한다.
2. 전용 프로젝트를 만들거나 인수인계 대상 프로젝트를 선택한다.
3. OAuth consent screen의 앱 이름, 지원 이메일, 공개 범위와 테스트 사용자를 설정한다.
4. Web application OAuth client를 생성한다.
5. 아래 Redirect URI를 등록하고 Client ID·Client Secret을 Backend Secret으로 저장한다.

| 환경 | Redirect URI |
| --- | --- |
| Local | `http://localhost:5173/auth/callback/google` |
| Production | `https://l1mit.shop/auth/callback/google` |

환경변수:

- `GOOGLE_OAUTH_ENABLED`
- `GOOGLE_OAUTH_CLIENT_ID`
- `GOOGLE_OAUTH_CLIENT_SECRET`
- `GOOGLE_OAUTH_REDIRECT_URIS`

### 2.2 Kakao Login

공식 문서: [Kakao Login REST API](https://developers.kakao.com/docs/ko/kakaologin/rest-api)

가입·설정:

1. 조직이 관리하는 Kakao 계정으로 Kakao Developers에 로그인한다.
2. 애플리케이션을 만들고 Web 플랫폼의 사이트 도메인을 등록한다.
3. Kakao Login을 활성화하고 필요한 동의 항목을 검토한다.
4. Redirect URI를 등록한다.
5. REST API Key에 대응하는 Client ID와 Client Secret을 Backend Secret으로 저장한다.

| 환경 | Redirect URI |
| --- | --- |
| Local | `http://localhost:5173/auth/callback/kakao` |
| Production | `https://l1mit.shop/auth/callback/kakao` |

환경변수:

- `KAKAO_OAUTH_ENABLED`
- `KAKAO_OAUTH_CLIENT_ID`
- `KAKAO_OAUTH_CLIENT_SECRET`
- `KAKAO_OAUTH_REDIRECT_URIS`

### 2.3 NAVER Login

공식 문서: [NAVER 로그인 API](https://developers.naver.com/docs/login/api/)

가입·설정:

1. 조직이 관리하는 NAVER 계정으로 NAVER Developers에 로그인한다.
2. 애플리케이션을 등록하고 사용 API로 NAVER 로그인을 선택한다.
3. 제공할 회원 정보와 서비스 URL을 지정한다.
4. Callback URL을 등록한다.
5. Client ID·Client Secret을 Backend Secret으로 저장한다.

| 환경 | Callback URL |
| --- | --- |
| Local | `http://localhost:5173/auth/callback/naver` |
| Production | `https://l1mit.shop/auth/callback/naver` |

환경변수:

- `NAVER_OAUTH_ENABLED`
- `NAVER_OAUTH_CLIENT_ID`
- `NAVER_OAUTH_CLIENT_SECRET`
- `NAVER_OAUTH_REDIRECT_URIS`

## 3. Toss Payments

공식 문서: [Toss Payments 연동 가이드](https://docs.tosspayments.com/en/integration)

가입·설정:

1. 조직 명의 Toss Payments 개발자센터·상점 계정을 준비한다.
2. 개발 단계에서는 테스트 키로 승인·취소·실패 경로를 검증한다.
3. 운영 전 계약·심사 후 라이브 키로 전환한다.
4. 결제 성공·실패 redirect URL과 webhook 수신 URL을 실제 도메인 기준으로 등록한다.
5. webhook 서명 검증용 Security Key를 Backend Secret으로 저장한다.

환경변수:

| 위치 | 변수 | 공개 여부 |
| --- | --- | --- |
| Backend | `TOSS_PAYMENTS_SECRET_KEY` | Secret |
| Backend | `TOSS_PAYMENTS_SECURITY_KEY` | Secret |
| Backend | `TOSS_PAYMENTS_API_VERSION` | 설정값 |
| Frontend | `VITE_TOSS_PAYMENTS_CLIENT_KEY` | 브라우저 공개 client key |

테스트 키와 라이브 키를 혼용하지 않는다. Secret Key와 Security Key를 `VITE_*`에 넣지 않는다. 실제 상점 ID·키 종류·webhook URL은 콘솔에서 확인해야 하며 이 문서에서는 임의로 만들지 않는다.

## 4. AWS와 Cloudflare

### 4.1 AWS S3 미디어 저장소

공식 문서: [S3 presigned URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html), [S3 보안 모범 사례](https://docs.aws.amazon.com/AmazonS3/latest/userguide/security-best-practices.html)

용도:

- 상품 이미지·영상
- 검수 증빙
- 채팅 미디어
- 선택적 DB backup
- Backend가 발급하는 제한 시간 presigned upload/download URL

가입·설정:

1. 조직 AWS 계정에서 `ap-northeast-2` 리전의 미디어 bucket을 준비한다.
2. Block Public Access를 유지하고 필요한 CORS만 허용한다.
3. EC2 Backend에는 Instance Profile을 우선 사용한다.
4. 정적 access key가 불가피하면 최소 권한 IAM 사용자로 제한하고 주기적으로 회전한다.
5. 운영 bucket명, lifecycle, versioning, 암호화, upload prefix 정책을 인수인계한다.

환경변수:

- 인증·리전: `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`
- S3: `S3_MEDIA_BUCKET`, `S3_ENDPOINT`, `S3_PATH_STYLE_ACCESS`
- URL: `S3_UPLOAD_TTL`, `S3_DOWNLOAD_TTL`, `S3_PUBLIC_BASE_URL`
- 후처리: `S3_UPLOAD_CLEANUP_DELAY_MS`, `S3_UPLOAD_CLEANUP_INITIAL_DELAY_MS`, `S3_FFPROBE_ENABLED`, `S3_FFPROBE_EXECUTABLE`, `S3_FFPROBE_TIMEOUT`
- Backup: `BACKUP_UPLOAD_ENABLED`, `BACKUP_S3_URI`, `BACKUP_KMS_KEY_ID`, `BACKUP_LOCAL_RETENTION_DAYS`

### 4.2 AWS Frontend 인프라

저장소의 `infra/terraform/frontend`가 다음 리소스를 정의한다.

- private S3 website artifact bucket
- CloudFront OAC와 HTTPS distribution
- Vue Router fallback용 CloudFront Function
- ACM 인증서와 선택적 WAF
- GitLab OIDC 기반 배포 IAM role

가입·설정:

1. Terraform state를 애플리케이션 bucket과 분리해 준비한다.
2. custom domain 사용 시 `us-east-1` ACM 인증서를 발급·검증한다.
3. GitLab OIDC provider와 배포 role을 만들고 trust policy를 해당 GitLab 프로젝트의 보호 브랜치로 제한한다.
4. Terraform output을 GitLab protected variable에 등록한다.

GitLab 변수:

- `AWS_DEPLOY_ROLE_ARN`
- `FRONTEND_BUCKET_NAME`
- `CLOUDFRONT_DISTRIBUTION_ID`
- `FRONTEND_PUBLIC_URL`
- `VITE_API_BASE_URL`

기존 운영 문서에는 OIDC provider와 배포 role이 아직 생성되지 않았다는 기록이 있다. 실제 AWS·GitLab 상태를 다시 확인해야 하며, 미구성 상태에서는 Frontend 자동 배포의 AWS 인증이 실패한다.

### 4.3 Cloudflare DNS

공식 문서: [Cloudflare DNS record 관리](https://developers.cloudflare.com/dns/manage-dns-records/)

용도:

- `l1mit.shop`, `www.l1mit.shop`의 Frontend 레코드
- `api`, `admin`, `docs`, `grafana` 서브도메인의 EC2 진입점 레코드

가입·설정:

1. 조직 Cloudflare 계정에 `l1mit.shop` zone을 연결한다.
2. Terraform용 API Token은 해당 zone의 DNS edit 최소 권한만 부여한다.
3. `infra/terraform/dns`에서 plan을 검토한 뒤 승인된 작업자가 apply한다.
4. 토큰은 로컬 임시 환경변수 `CLOUDFLARE_API_TOKEN`으로만 전달하고 Git에 저장하지 않는다.

현재 운영 절차는 EC2 서브도메인을 DNS-only CNAME으로 관리한다. root와 `www` Frontend 레코드 및 ACM 검증 레코드는 별도 Frontend 인프라와 충돌하지 않도록 DNS Terraform에서 제외한다.

## 5. AI와 OCR

### 5.1 OpenAI API: 런타임 체크리스트

공식 문서: [OpenAI API Quickstart](https://developers.openai.com/api/docs/quickstart)

용도: 기기 모델에 따른 검사 체크리스트를 보강한다. 기능이 꺼져 있거나 외부 호출이 실패하면 검증된 기본 체크리스트를 사용한다.

가입·설정:

1. 조직 OpenAI API 프로젝트를 준비하고 결제·사용 한도를 설정한다.
2. 서버 전용 API key를 발급한다.
3. key를 운영 `infra/.env` 또는 Secret 관리 체계에 저장한다.
4. 허용 도메인, timeout, 실제 프로젝트에서 사용 가능한 모델을 점검한 뒤 기능을 활성화한다.

환경변수:

- `AI_CHECKLIST_ENABLED=false`
- `OPENAI_API_KEY`
- `OPENAI_RESPONSES_ENDPOINT=https://api.openai.com/v1/responses`
- `OPENAI_CHECKLIST_MODEL=gpt-5.6-luna`
- `AI_CHECKLIST_ALLOWED_DOMAINS`
- `AI_CHECKLIST_CONNECT_TIMEOUT=5s`
- `AI_CHECKLIST_READ_TIMEOUT=30s`

`gpt-5.6-luna`는 현재 저장소에 고정된 설정값을 그대로 기록한 것이다. 실제 OpenAI 프로젝트의 모델 접근 가능 여부는 계정 콘솔과 호출 테스트로 확인해야 하며, 확인 없이 다른 모델명으로 바꾸지 않는다. `OPENAI_API_KEY`는 Backend 전용이며 Frontend나 로그에 노출하지 않는다.

### 5.2 NAVER CLOVA OCR

공식 문서: [CLOVA OCR API](https://api.ncloud-docs.com/docs/en/ai-application-service-ocr)

가입·설정:

1. 조직 NAVER Cloud Platform 계정을 준비한다.
2. CLOVA OCR domain을 생성하고 사용할 OCR template·API endpoint를 준비한다.
3. Invoke URL과 Secret Key를 운영 Backend Secret으로 저장한다.
4. 허용 포맷, 크기 제한, 과금·호출 한도를 검토한다.

환경변수:

- `NAVER_CLOVA_OCR_INVOKE_URL`
- `NAVER_CLOVA_OCR_SECRET_KEY`

Secret Key는 `X-OCR-SECRET` 요청 헤더에 사용되므로 Frontend와 로그에 노출하지 않는다.

## 6. 이메일과 RTC

### 6.1 SMTP

용도:

- 회원 이메일 인증
- 비밀번호 재설정
- Alertmanager 운영 알림

환경변수:

- `MAIL_HOST` (예시 기본값 `smtp.gmail.com`)
- `MAIL_PORT` (예시 기본값 `587`)
- `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM`
- `MAIL_SMTP_AUTH`, `MAIL_STARTTLS_ENABLED`
- `EMAIL_VERIFICATION_DELIVERY_ENABLED`
- `PASSWORD_RESET_DELIVERY_ENABLED`
- Alertmanager: `ALERTMANAGER_SMTP_PASSWORD_FILE`

가입·설정:

1. 개인 계정이 아닌 운영 전용 발신 계정을 준비한다.
2. 공급자가 요구하면 2단계 인증과 앱 비밀번호 또는 SMTP 전용 자격증명을 사용한다.
3. From 주소와 SPF·DKIM·DMARC 정책을 설정한다.
4. 인증·재설정 링크 도메인과 Alertmanager 수신자를 시험한다.

### 6.2 STUN·TURN

- 기본 STUN: `stun:stun.l.google.com:19302` — public STUN이므로 별도 가입 정보가 없다.
- TURN: 운영 EC2의 self-hosted coturn을 사용한다.

환경변수:

- `RTC_ALLOWED_ORIGIN_PATTERNS`
- `RTC_STUN_URL`
- `RTC_TURN_URL`
- `RTC_TURN_USERNAME`
- `RTC_TURN_CREDENTIAL`
- `RTC_TURN_REALM`

TURN username·credential은 서버 Secret이다. UDP/TCP/TLS 포트와 보안그룹, NAT 환경, 실제 브라우저 간 통화를 함께 시험한다.

## 7. CI·품질·운영 서비스

### 7.1 GitLab

공식 문서: [GitLab CI/CD 변수](https://docs.gitlab.com/ci/variables/)

필요 설정:

- `dev`와 향후 `main` protected branch 및 MR 정책
- GitLab Runner
- protected/masked/file CI/CD Variables
- scheduled dependency scan
- Frontend AWS OIDC ID token
- 수동 rollback 권한

현재 원격에는 `main`이 없으므로 저장소 규칙·CI의 `main` 조건과 실제 브랜치 정책을 먼저 일치시켜야 한다. `origin/master`를 임의로 운영 브랜치로 사용하지 않는다.

### 7.2 Docker Hub

공식 문서: [Docker personal access token](https://docs.docker.com/security/access-tokens/)

가입·설정:

1. 조직 namespace 아래 private Backend repository를 만든다.
2. CI에는 push 가능한 전용 token을 사용한다.
3. EC2에는 CI token과 다른 read-only token으로 `docker login`한다.

GitLab 변수:

- `DOCKERHUB_IMAGE`
- `DOCKERHUB_USERNAME`
- `DOCKERHUB_TOKEN`

### 7.3 Sentry

공식 문서: [Sentry Vue SDK](https://docs.sentry.io/platforms/javascript/guides/vue/)

가입·설정:

1. 조직 Sentry 프로젝트를 Vue 플랫폼으로 만든다.
2. Frontend DSN과 환경명을 빌드 변수에 넣는다.
3. sourcemap 업로드용 조직·프로젝트 slug와 auth token을 GitLab masked/protected 변수로 등록한다.

변수:

- Frontend 공개 설정: `VITE_SENTRY_DSN`, `VITE_SENTRY_ENVIRONMENT`, `VITE_SENTRY_RELEASE`
- CI Secret: `SENTRY_ORG`, `SENTRY_PROJECT`, `SENTRY_AUTH_TOKEN`

DSN은 브라우저에 포함되는 식별자지만 auth token은 Secret이다.

### 7.4 SonarCloud

용도: Backend 정적 분석과 quality gate. 저장소의 프로젝트 설정은 `sonar-project.properties`와 `.gitlab-ci.yml`을 기준으로 한다.

가입·설정:

1. 조직 SonarCloud 계정에 프로젝트를 연결한다.
2. 분석 token을 발급한다.
3. `SONAR_HOST_URL`, `SONAR_TOKEN`을 GitLab 변수로 등록한다.
4. main branch 명칭과 quality gate를 실제 GitLab 브랜치 정책에 맞춘다.

### 7.5 NVD API

용도: OWASP Dependency-Check의 취약점 데이터 조회 한도를 높이고 초기 동기화를 단축한다.

가입·설정:

1. NVD에서 API key를 신청한다.
2. `NVD_API_KEY`를 GitLab masked/protected 변수로 등록한다.
3. GitLab Pipeline Schedule을 등록한다.

이 키는 Backend 런타임 `.env`에 넣지 않는다.

### 7.6 SSAFY GMS와 PR-Agent

용도: Merge Request 자동 리뷰. Backend 런타임의 OpenAI API와 별도 서비스·별도 key다.

GitLab 변수:

- `GITLAB_PERSONAL_ACCESS_TOKEN`: MR 조회·댓글 작성용 최소 `api` 권한의 bot 또는 project token
- `OPENAI_KEY`: SSAFY GMS key
- `SKIP_PR_AGENT`: 긴급 시 child pipeline 생성을 생략하는 선택 변수

저장소 설정은 GMS 호환 base URL `https://gms.ssafy.io/gmsapi/api.openai.com/v1`과 리뷰 모델 `gpt-5-mini`를 사용한다. 이 값들을 런타임 `OPENAI_API_KEY`·`OPENAI_CHECKLIST_MODEL`과 혼용하지 않는다.

### 7.7 Let's Encrypt

용도: `api`, `admin`, `docs`, `grafana` EC2 진입점의 HTTPS 인증서. `scripts/provision-ec2-entrypoints.sh`가 Nginx와 HTTP-01 절차를 구성한다.

인수인계 시 확인:

- 인증서에 등록된 도메인
- Certbot 등록 이메일
- 자동 갱신 timer 상태
- 80 포트의 ACME challenge 접근
- 갱신 후 Nginx reload

인증서 개인키는 운영 서버 밖으로 복사하거나 저장소에 넣지 않는다.

## 8. 계정 인수인계 체크리스트

각 외부 서비스에 대해 다음 항목만 별도의 보안 채널로 인수인계한다.

- 조직·프로젝트 소유자와 비상 연락 담당자
- 2단계 인증과 복구 수단
- 과금 계정·예산 경보·사용 한도
- 운영/개발 환경 분리 여부
- 발급된 자격증명의 용도·권한·만료일·마지막 회전일
- 등록된 callback, webhook, CORS, allowed origin, domain
- GitLab 변수명과 실제 Secret 저장 위치
- 계정 탈퇴·담당자 변경 시 회전해야 할 key 목록

실제 식별정보를 추가 문서화해야 한다면 저장소 문서가 아니라 접근 제어된 사내 비밀 저장소를 사용한다.
