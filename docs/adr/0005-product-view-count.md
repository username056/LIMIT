# ADR-0005: 상품 조회수를 MySQL 원자 증가로 집계

- 상태: Accepted
- 결정일: 2026-08-01
- 관련: [ADR-0003](0003-device-catalog-split.md)

## 배경

공개 상품 목록에 인기순 정렬이 없다. 구매자는 최신순과 가격순으로만 훑을 수 있어, 실제로 관심이
몰린 매물을 찾을 방법이 없다.

기획서는 Redis로 실시간 조회수(`INCR`)와 인기 순위(Sorted Set)를 두고 주기적으로 MySQL에
동기화하는 구조를 제시했다.

## 결정

### 1. Redis 대신 MySQL 원자 증가를 쓴다

```sql
UPDATE listing SET view_count = view_count + 1
 WHERE id = ? AND status = 'ON_SALE' AND deleted_at IS NULL
```

Redis 구조는 저장소가 하나 더 늘고, 카운터와 Sorted Set의 이중 기록, 주기 동기화, 장애 시 폴백,
두 저장소 간 불일치 처리를 모두 떠안는다. 지금 규모에서 그 복잡도를 정당화할 트래픽이 없다.

MySQL 한 문장이면 정렬까지 같은 쿼리에서 끝난다. 별도 순위 자료구조가 필요 없고, 조회수와
매물 상태가 항상 같은 트랜잭션 경계 안에 있어 어긋날 여지도 없다.

트래픽이 늘어 이 UPDATE가 병목이 되면 그때 Redis를 앞에 두면 된다. `view_count` 열은 그
구조에서도 영속 스냅샷으로 그대로 쓰인다.

### 2. 엔티티를 읽어 +1 하지 않는다

읽고 더해 저장하면 동시 조회에서 갱신이 유실된다. 상세 조회는 서비스에서 동시성이 가장 높은
경로라 실제로 발생하고, 그대로 두면 인기순 정렬의 근거가 무너진다. 통합 테스트에서 16 스레드가
각각 25회씩 총 400회를 동시에 올려 유실이 없음을 확인한다.

### 3. 벌크 갱신이라 `@Version`을 건드리지 않는다 — 의도한 바다

조회수가 낙관적 락 버전을 올리면, 누군가 상세를 보는 것만으로 판매자의 상품 수정이 충돌로
실패할 수 있다. 조회는 판매자의 편집과 경합해서는 안 된다.

### 4. 별도 트랜잭션에서 집계한다

`ProductViewCountRecorder`가 `REQUIRES_NEW`로 실행되고 예외를 삼킨다. 집계는 부가 기능이고,
이것 때문에 상세 조회가 실패하면 손해가 훨씬 크다. 상세 조회가 읽기 전용 트랜잭션이라 같은
트랜잭션에서 쓸 수도 없다.

순서는 증가 → 조회다. 반대로 하면 방금 올린 자기 조회가 응답에 안 보여 집계가 안 되는 것처럼
보인다.

### 5. 공개 상태가 아닌 매물은 집계하지 않는다

숨김·판매 완료·삭제된 매물의 조회수가 올라가면 인기순이 그 매물을 끌어올린다. 조건을 UPDATE의
WHERE에 넣어, 갱신 행 수 0으로 호출부가 집계되지 않았음을 알 수 있게 한다.

### 6. 인기순은 공개 목록에만 연다

`GET /api/v1/products`의 `sort`에 `viewCount`를 추가한다. 판매자 본인 목록은 내 상품을 관리하는
화면이라 인기순으로 볼 이유가 없다.

## 결과와 제한

- **중복 조회 방지가 없다.** 같은 사용자가 새로고침하면 그만큼 올라간다. 30분 단위 중복 제외는
  조회자 식별과 만료가 필요해 Redis나 별도 테이블이 있어야 한다. 그 전까지 인기순은 "많이 열린
  순"으로만 읽어야 하고, 판매자가 자기 매물을 반복 조회해 순위를 올리는 것도 막지 못한다.
- 판매자 본인의 미리보기도 집계된다. 위와 같은 이유다.
- 상세 조회마다 UPDATE가 한 번 더 나간다. 별도 트랜잭션이라 커밋도 한 번 더 발생한다. 부하
  테스트로 실제 지연 증가를 측정해야 한다.
- 인덱스는 `idx_listing_view_count_feed (status, deleted_at, view_count DESC)`를 쓴다
  (V20260814에서 추가).
