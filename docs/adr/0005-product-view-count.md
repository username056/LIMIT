# ADR-0005: 상품 조회수를 비동기 MySQL 원자 증가로 집계

- 상태: Accepted
- 결정일: 2026-08-01
- 수정일: 2026-08-02
- 관련: [ADR-0003](0003-device-catalog-split.md)

## 배경

공개 상품 상세가 얼마나 열렸는지 보여 줄 조회수가 필요하다. 기획서는 Redis 실시간 카운터와
인기 순위를 제시했지만, 현재 규모에서 두 저장소 동기화까지 운영할 근거는 부족하다.

조회수는 상세 응답의 부가 기능이므로 DB 지연이나 장애가 상세 조회를 막아서는 안 된다. 또한 같은
매물에 대한 조회와 판매자의 수정이 겹쳐도 어느 한쪽의 값을 잃어서는 안 된다.

## 결정

### 1. MySQL에서 원자 증가한다

```sql
UPDATE listing SET view_count = view_count + 1
 WHERE id = ? AND status = 'ON_SALE' AND deleted_at IS NULL
```

엔티티를 읽어 더한 뒤 저장하지 않으므로 조회수끼리의 동시 갱신을 잃지 않는다. 공개 상태가 아닌
매물은 WHERE 조건에서 걸러 낸다. 트래픽이 실제 병목 수준으로 증가하면 `view_count`를 영속
스냅샷으로 유지한 채 Redis를 앞에 둘 수 있다.

### 2. 상세 응답과 집계 실행을 분리한다

상세 응답을 먼저 구성하고 `ProductViewCountDispatcher`가 전용 bounded executor에서 집계를
실행한다. `ProductViewCountRecorder`는 `REQUIRES_NEW` 트랜잭션으로 UPDATE를 커밋한다.

디스패처가 Recorder 프록시 바깥에서 예외를 처리하므로 쿼리 실행뿐 아니라 트랜잭션 종료·커밋
단계의 실패도 상세 응답으로 전파되지 않는다. 실행기는 최대 스레드와 대기열을 제한하며, 대기열이
가득 차 예약이 거절된 경우에도 상세 조회는 정상 응답한다. 요청의 MDC `traceId`는 작업 실행
스레드로 전달해 실패 로그를 원래 요청과 연결한다.

### 3. 조회수와 판매자 수정을 서로 덮어쓰지 않는다

조회수 벌크 UPDATE는 `@Version`을 올리지 않는다. 조회만으로 판매자의 수정이 낙관적 락 충돌을
일으키지 않게 하기 위해서다.

대신 `Listing`에 `@DynamicUpdate`를 적용해 판매자 수정이 실제로 바꾼 열만 UPDATE한다. 판매자
트랜잭션이 증가 전의 조회수를 읽었더라도 그 오래된 값을 다시 쓰지 않는다. 통합 테스트에서
`Listing`을 읽은 뒤 별도 조회수 트랜잭션을 커밋하고 판매자 수정을 flush해 증가분 보존을 검증한다.

### 4. 조회수 정렬은 한계를 표시하고 제공한다

같은 사용자·판매자·봇의 반복 조회를 구분할 식별자와 만료 정책이 아직 없다. 따라서 조회수 값은
목록 응답과 상품 카드에 제공하고 `viewCount,desc` 정렬도 연다. 다만 이를 검증된 인기도로 표현하지
않고 "조회수 높은 순"으로 표시하며, 반복 조회가 포함된 누적값이라는 안내를 함께 노출한다. 조회자
식별과 30분 단위 중복 제외는 순위 신뢰도를 높이는 별도 후속 작업으로 둔다.

## 결과와 제한

- 같은 사용자가 새로고침하면 조회수가 다시 올라가며 판매자 본인의 공개 상세 조회도 포함된다.
- 비동기 집계라 상세 응답 직후 목록을 다시 조회하면 증가분이 아직 보이지 않을 수 있다.
- 실행 대기열이 가득 차거나 DB가 실패하면 조회수 일부를 버린다. 사용자 조회 성공을 우선한
  의도적인 best-effort 정책이다.
- `idx_listing_view_count_feed (status, deleted_at, view_count DESC)`를 조회수 정렬에 사용한다.
- 조회수가 같은 상품은 `created_at DESC, id DESC`로 정렬해 페이지 결과를 안정적으로 유지한다.
