# 성능 분석

## 먼저 읽을 근거

1. 루트와 대상 폴더의 `AGENTS.md`
2. 도구별 `harness/performance.md`
3. 대상 도메인의 Controller, Service, Repository, Entity와 인접 테스트
4. 필요할 때 `k6-load-test`, `sql-query-analysis`, `observability-analysis` 스킬

## 작업 순서

1. 요청 빈도, 목록·검색, 반복 조회, 복잡한 join, pagination, 외부 호출, 넓은 transaction, lock 경합 후보를 코드 근거와 함께 나열한다.
2. 측정 가능성과 사용자 영향도를 기준으로 대상 API 또는 사용자 흐름 하나를 우선 선정한다. 측정 전에는 모두 가설로 표시한다.
3. 기능 성공 조건과 성능 목표를 분리해 정의하고 코드를 바꾸기 전에 Baseline을 측정한다.
4. k6 결과를 같은 구간의 SQL·JVM·인프라 지표와 연결해 병목 가설을 확인하거나 기각한다.
5. 최소 두 개선 후보를 비교한다. 예: fetch 전략, projection, batch, query 변경, index, cache, transaction 축소, 비동기화, pool 조정.
6. 가장 직접적인 근거가 있는 최소 변경을 선택하고 제외한 후보의 이유도 기록한다. 새로운 운영 복잡성은 성능 수치만큼 명시한다.
7. 기능 회귀 검증 후 동일 조건으로 재측정한다. 결과가 개선되지 않으면 성공으로 표현하지 말고 원인과 다음 가설을 남긴다.

## 산출물

다음 구조를 사용한다.

### 문제

대상 API와 호출 구조, 가설, Baseline 실측값과 근거 위치를 적는다.

### 의사결정 과정

병목 확인·기각 근거, 후보 비교, 선택과 제외 이유, 구현 범위와 부작용을 적는다.

### 결과

동일 조건의 Before/After 표, 개선율, 기능 검증 결과, 남은 위험을 적는다. 측정하지 않은 값은 `N/A`로 표시한다.

## 완료 기준

Baseline 원본, 비교 조건, 병목 근거, 후보 비교, 기능 검증, 동일 조건 After가 모두 있어야 개선 완료로 표시한다. 승인 없는 운영 부하, migration, 배포나 설정 변경은 수행하지 않는다.
